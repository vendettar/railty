## 4. Reproduction recipe (run on an Xcode-capable Mac)

```bash
# 1. Build benchmarks (needs full Xcode for metallib)
zig build -Demit-bench -Doptimize=ReleaseFast -Demit-macos-app=false

# 2. Deterministic corpora
zig-out/bin/ghostty-gen ascii > /tmp/ascii.vt
zig-out/bin/ghostty-gen styled-heavy > /tmp/styled-heavy.vt

# 3. Terminal throughput (warmup + repeated runs; record median and spread)
hyperfine --warmup 3 --runs 10 \
  'zig-out/bin/ghostty-bench +terminal-stream --data=/tmp/ascii.vt --scrollback=50MB'

# 4. Resize / reflow
hyperfine --warmup 3 --runs 10 \
  'zig-out/bin/ghostty-bench +terminal-resize --data=/tmp/ascii.vt'

# 5. Snapshot codecs
hyperfine --warmup 3 --runs 20 \
  'zig-out/bin/ghostty-bench +terminal-snapshot --mode=encode --loops=20 --data=/tmp/ascii.vt' \
  'zig-out/bin/ghostty-bench +terminal-snapshot --mode=decode --loops=20 --data=/tmp/ascii.vt'
```

Measurement rules:

- Same machine, same power state, same build mode (`ReleaseFast`), same corpus and dimensions.
- Warm up before timing; run at least 5 repetitions; report median and min/max.
- Never treat GitHub Actions build-duration changes as terminal throughput improvements.

## 6. PageList prune-memory measurement (2026-11-17, Xcode installed)

Purpose: verify `d0addb9cdf` on Railty's own code before deciding on merge.

Setup:

- Same host, `ReleaseFast`, benchmarks built with `zig build -Demit-bench -Doptimize=ReleaseFast -Demit-macos-app=false`.
- Corpus: 1 GiB of newline-terminated 199-column ASCII lines (forces scrollback growth and line-limit pruning; the stock `ghostty-gen +ascii` corpus has no newlines and does not exercise this path).
- Command: `ghostty-bench +terminal-stream --terminal-rows=50 --terminal-cols=200 --max-lines=<N> --max-bytes=10000000000 --data=/tmp/railty-lines-1g.vt`
- The byte limit is raised because the terminal default is 10,000 bytes, which masks line-limit behavior.
- Five alternating runs per binary; median reported. Baseline = `main` without the fix; prune = branch `sync/ghostty-pagelist-prune-memory` (`04c6deea1`).

| Scenario | Baseline | Prune | Speedup |
|---|---:|---:|---:|
| max-lines 1,000, bytes 10 GB | 674 MB/s (1.594 s) | 1,115 MB/s (0.963 s) | **1.65x** |
| max-lines 10,000, bytes 10 GB | 729 MB/s (1.472 s) | 1,244 MB/s (0.863 s) | **1.71x** |
| no line limit, bytes 10 GB | 422 MB/s (2.542 s) | 438 MB/s (2.449 s) | 1.04x (noise) |

Peak RSS, one run at max-lines 1,000:

| Binary | Real | User | Sys | Max RSS |
|---|---:|---:|---:|---:|
| baseline | 1.37 s | 0.70 s | 0.65 s | 11.06 MB |
| prune | 0.79 s | 0.70 s | 0.08 s | 10.90 MB |

Interpretation: user CPU is identical; the win is almost entirely eliminated kernel time from decommit/fault churn, matching the upstream explanation. Retaining one pooled page did not increase measured RSS here.

Remaining `NOT_TESTED`: GUI launch/quit, tabs/vertical tabs, sidebar, Git panel, clipboard, shell integration, `railtyctl`, and the carriage-return experiment.
